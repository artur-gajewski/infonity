# Memory latency benchmark

Measured on 2026-11-02 using local Ollama and environment/default model settings,
three runs, ten synthetic background memories, and a temporary database:

```sh
.venv/bin/python scripts/benchmark_memory.py --runs 3 --size 10
```

| Stage (milliseconds) | Run 1 | Run 2 | Run 3 |
| --- | ---: | ---: | ---: |
| Save total | 5060 | 3258 | 2879 |
| Model extraction | 4552 | 2519 | 2345 |
| Model verification | 499 | 728 | 526 |
| SQLite work during save | 9 | 11 | 9 |
| Index total | 773 | 6 | 5 |
| Embedding calls during indexing | 694 | 0 | 0 |
| Indexed records | 11 | 0 | 0 |
| Retrieval total | 92 | 45 | 31 |
| Query embedding | 83 | 35 | 23 |
| SQLite work during retrieval | 9 | 10 | 7 |
| First visible answer text | 3420 | 3429 | 5316 |

All measured stages succeeded. Repeated saves deduplicated the same synthetic fact,
so later indexing runs had no new work. The provider buffers answer output for
thinking filtering; first visible text is not the first token generated by Ollama.

In this small test, extraction and verification dominate saving; query embeddings
dominate retrieval. These results do not justify replacing SQLite. They do not
measure the user's live corpus, concurrent worker load, intent interpretation,
HTTP overhead, or browser latency. Run 1 was not forced cold. Saved application
settings were not read. See the README for benchmark usage and timing definitions.
